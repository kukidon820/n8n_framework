# Архитектура

## Назначение

Конвертер читает исходный n8n JSON только при генерации. Он разбирает список узлов, канал main и поддерживаемые expressions, после чего записывает самостоятельный Python-проект. В generated-проекте нет движка n8n и обязательной зависимости от исходного JSON.

Линейные шаги становятся явными async-вызовами функций в <code>main.py</code>. IF и Switch создают ветвления, Merge объединяет входы, Loop асинхронно управляет циклом. Подключённая chat-модель служит конфигурацией Agent, а не отдельным шагом исполнения.

Каждый поддерживаемый тип узла может встречаться в workflow несколько раз без общего лимита. Для проверки структуры используются уникальные имена и ID узлов. В главном графе должна быть одна начальная точка; циклы, кроме обратной связи Loop, не допускаются.

## Этапы конвертации

1. <code>reader.py</code> читает JSON и проверяет его базовую структуру.
2. <code>graph.py</code> преобразует connections в ориентированные связи и вычисляет порядок узлов по каналу main.
3. <code>expressions.py</code> разбирает поддерживаемое подмножество expressions во время генерации и формирует зависимости от результатов предыдущих узлов.
4. <code>versioning.py</code> предупреждает о непроверенных версиях, выбирает fallback там, где он задан, и готовит безопасную подсказку для ручной доработки.
5. Модули в <code>converters/</code> создают конкретные функции и классы для реализованных типов узлов.
6. <code>generator.py</code> строит imports и вызовы в <code>main.py</code>, готовит <code>config.py</code>, README, conversion report и файлы зависимостей.
7. CLI при записи проекта запускает <code>uv lock</code>, чтобы положить в output каталог lock-файл.

## Частичная конвертация

Генератор разделяет неполную поддержку параметров узла и отсутствие поддержки самого узла.

Для поддерживаемого типа неизвестный параметр, режим или неподдерживаемое expression может превратиться в TODO-функцию в отдельном модуле. Она сохраняет место узла в графе, содержит безопасное описание параметров без исходных значений и сообщает о незавершённой реализации через <code>NotImplementedError</code>. Некоторые общие настройки исполнения, отсутствующие credentials и неподдерживаемые соединения приводят к пропуску узла. Причина и итоговый статус попадают в комментарии <code>main.py</code>, generated README и <code>conversion_report.md</code>; подробные случаи перечислены в [ограничениях](limitations.md).

Если генератор не знает тип узла или соединения либо не находит обязательную ссылку на credentials, соответствующая часть исключается. Связи через исключённые узлы могут быть упрощены, но это не восстанавливает семантику пропущенного шага. Поэтому после конвертации нужно проверить входы соседних функций и вручную реализовать пропущенную обработку.

<code>validate</code> обходит весь workflow и сообщает накопленные диагностики; при блокирующих проблемах, например отсутствующих обязательных credentials или неподдерживаемом соединении, команда завершается с ненулевым кодом. <code>convert</code> всё равно пытается записать доступную часть проекта и отчёт. Некорректный JSON и workflow без узлов требуют исправления исходного файла.

Trigger-узлы не входят в исполняемый граф и не запускаются; проверка порядка workflow не требует ставить их первыми. Их имя, тип и параметры сохраняются в README сгенерированного проекта; его <code>main.py</code> предназначен для ручного запуска.

## Структура исходного пакета

    src/n8n_transcriper/
    ├── cli.py                 Typer CLI: convert, inspect, validate
    ├── reader.py              чтение и проверка JSON
    ├── graph.py               связи и порядок узлов
    ├── expressions.py         компиляция expressions
    ├── versioning.py          fallback версий и предупреждения
    ├── generator.py           план генерации, main.py и отчёты
    └── converters/
        ├── ai.py              AI Agent и chat-модели
        ├── code.py            Python Code
        ├── conditions.py      IF и Switch
        ├── data_table.py      Data Table и асинхронный helper PostgreSQL
        ├── edit_fields.py     Edit Fields / Set
        ├── files.py           Convert to File, Compression, Extract From File
        ├── http.py            HTTP Request
        ├── loop.py            Loop Over Items
        ├── wait.py            Wait и асинхронная пауза
        ├── merge.py           Merge Append и Combine
        ├── postgres.py        PostgreSQL executeQuery
        └── smtp.py            Send Email и Gmail raw MIME через SMTP

Каждый converter содержит знания о параметрах своего типа узла. Неизвестные поля не интерпретируются по имени узла. Полный список поддерживаемых параметров приведён в [справочнике узлов](supported-nodes.md).

Дополнительная реализация режима LangGraph расположена в <code>src/n8n_transcriper/langgraph_mode/</code>: <code>detection.py</code> определяет AI-вызовы, <code>providers.py</code> хранит endpoints, <code>agent_generation.py</code> генерирует адаптеры моделей, а <code>renderer.py</code> строит точку запуска графа.

## Generated-проект

Каждая функция узла имеет async-интерфейс и вызывается через await. HTTP использует httpx.AsyncClient, SMTP — aiosmtplib, PostgreSQL — AsyncConnection psycopg, а Data Table — asyncpg. Для файловых и чисто вычислительных узлов async-интерфейс сохраняет обычную логику преобразования данных.

Результаты предыдущих узлов доступны generated-функциям, поскольку expressions уже преобразованы в Python-ссылки. Для linked-item semantics добавляются внутренние индексы связей. Они нужны при вычислении ссылок вида <code>$('Узел').item</code> и убираются из публичного результата.

Данные между функциями представлены items с полями <code>json</code> и <code>binary</code>. Binary содержит bytes, имя файла и MIME-тип. File-конвертеры используют стандартные библиотеки Python там, где это возможно; HTTP, SMTP и базы данных получают отдельные проектные зависимости.

Каждый Loop Over Items получает собственный экземпляр класса <code>Loop</code>. Можно создавать любое количество последовательных и вложенных циклов в обычном режиме и в режиме LangGraph. Передаются <code>batchSize</code>, <code>reset</code>, <code>executeOnce</code> и параметры <code>retryOnFail</code>; тело выполняется асинхронно, обратная связь возвращает накопленные items. Паузы при retry не блокируют event loop. Retry относится к внутренним переходам контроллера Loop; ошибки шагов в теле цикла обрабатываются настройками этих шагов. Каждый отдельный Loop должен иметь один начальный вход, непустое тело и одну обратную связь на вход 0 из тела; ветви body и done не должны пересекаться. Общее число Loop не ограничено, произвольные циклы вне Loop не поддерживаются.

Wait с режимом <code>timeInterval</code> использует <code>asyncio.sleep</code> для секунд, минут, часов и дней. Режим <code>specificTime</code> ожидает заданное <code>dateTime</code>. Режимы возобновления по webhook и форме пропускаются с причиной: standalone-проект не поднимает сервер и не хранит приостановленное исполнение.

AI Agent без tools становится HTTP-вызовом подключённой модели через OpenAI-compatible Chat Completions API. Дополнительные соединения Agent вроде <code>ai_tool</code> не исполняются. Если из-за такого соединения Agent пропущен, generated report указывает канал и причину; chat-модель, нужная только этому Agent, также пропускается.

Это описание относится к обычному режиму и его простому HTTP-адаптеру. В режиме <code>--langgraph</code> для AI Agent формируется LangChain-модель выбранного провайдера.

По умолчанию распознавание AI-вызовов внутри HTTP Request выключено: такой узел остаётся обычным HTTP-шагом. Опция <code>--langgraph</code> включает отдельный анализ POST JSON-запросов. Детектор сопоставляет host и путь известных провайдеров с формой тела; для собственного endpoint требуется более строгий набор признаков модели и генерации. Узел, распознанный как AI, превращается в вызов модели через LangGraph, а модель с одного узла может использоваться несколькими AI Agent. Провайдеры, формы запросов и ограничения перечислены в [справочнике](supported-nodes.md#http-запросы-к-модели-в-режиме-langgraph).

Для поддерживаемых credentials генерируются отдельные профили подключения, когда workflow ссылается на несколько разных credential ID. Имена переменных видны в generated <code>config.py</code>; значения секретов из workflow не переносятся.

Data Table выполняет запросы через asyncpg, а PostgreSQL executeQuery — через AsyncConnection psycopg 3. Значения передаются параметрами драйвера; имена таблиц и полей экранируются.

## Конфигурация и зависимости

Generated <code>config.py</code> получает секреты из переменных окружения и содержит только поля, необходимые данному workflow. Значения credentials из n8n не копируются.

<code>pyproject.toml</code> описывает зависимости конкретного generated-проекта. <code>uv.lock</code> фиксирует разрешённые версии для <code>uv sync --locked</code>. <code>requirements.txt</code> остаётся экспортом зависимостей для инструментов, которые его используют.
